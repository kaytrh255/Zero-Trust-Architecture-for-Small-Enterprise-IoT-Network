# Security model (current implementation)

## Authentication

`AuthService` hashes application passwords with BCrypt before persistence. `users.password_hash` stores only the BCrypt hash. Registration/profile responses never expose it. Login uses Spring Security's `DaoAuthenticationProvider`; unknown usernames and incorrect passwords receive the same generic response. Every request admitted to authentication is written to `authentication_attempt_audits` with normalized username, outcome, and timestamp; successful events include the authenticated user ID. Passwords, JWTs, and client IP addresses are not written to audit storage. Only ADMIN and SECURITY_ANALYST can search this separate append-only history.

`LoginRateLimiter` limits requests by `HttpServletRequest.getRemoteAddr()` using a bounded, in-memory fixed window (default 20 requests per 60 seconds). It ignores client-provided `X-Forwarded-For` values. Over-limit requests return HTTP `429` with `Retry-After` before password verification and are not inserted into the authentication audit table. This limiter is local to one backend process; deployments behind a proxy or with multiple replicas need a trusted-proxy configuration and shared limiter/gateway.

Successful login creates a signed JWT with subject, issue time, expiry, an access-token purpose, and the account's MFA-auth version. The key comes from `JWT_SECRET`; `JWT_EXPIRATION_SECONDS` controls access-token lifetime. `JwtAuthenticationFilter` verifies signature/expiry and reloads the current account, role, enabled status, and MFA-auth version for protected requests. Enabling or disabling MFA increments that version, immediately rejecting previously issued access tokens.

For MFA-enabled accounts, password verification issues only a five-minute signed challenge. Challenge IDs are tracked and consumed transactionally; a challenge token is rejected by the bearer-token filter and can be completed only once. Successful MFA verification creates the access token, and invalid attempts remain in the authentication-attempt ledger. MFA verification, required-enrollment setup/confirmation, and password/TOTP-sensitive account-security mutations share the bounded per-peer authentication rate limiter.

MQTT connections use TLS and verify the broker certificate against the generated local CA. The Java Paho clients use an explicit trust store and hostname verification; do not use an insecure TLS bypass. The Compose broker listens on TLS port `8883` only and is host-bound to loopback.

## TOTP MFA (Phase 21)

MFA enrollment is available only to ADMIN and SECURITY_ANALYST accounts. Optional enrollment from Account security requires a password recheck; mandatory enrollment immediately after password sign-in uses the short-lived enrollment challenge described below. A fresh 160-bit Base32 TOTP secret is delivered once with a ten-minute setup deadline; the pending and active secret columns hold AES-256-GCM ciphertext using a 96-bit random nonce and 128-bit authentication tag. `MFA_ENCRYPTION_KEY` must decode from Base64 to exactly 32 bytes and is supplied only to the backend. Losing or casually rotating that key makes active seeds unreadable; back it up in a deployment secret manager and rotate through a planned re-enrollment process.

TOTP uses HMAC-SHA1, six digits, 30-second steps, and accepts the current counter plus one adjacent counter in either direction. The user row is locked while verifying and stores the highest accepted counter, preventing a code from being replayed. Recovery codes contain 128 random bits, are displayed once after setup, and are stored only as SHA-256 hashes. They are row-locked and marked used in the same transaction as successful MFA login. Normal MFA disable requires the password and a fresh TOTP code; Phase 25 adds a distinct password-plus-unused-recovery-code recovery route, and Phase 26 lets a different MFA-enabled ADMIN recover another enabled privileged account. MFA changes, recovery-code consumption, code rotation, and admin recovery are captured in append-only `mfa_security_audits`; MFA seeds, setup URIs, passwords, challenge tokens, and raw recovery codes are excluded from audit history. New events include actor ID/username snapshots; pre-V17 history may have null actor fields.

TOTP remains optional when `MFA_REQUIRE_PRIVILEGED=false`; existing MFA-enabled accounts still complete a second factor at sign-in. The symmetric encryption key is external to PostgreSQL but is not a managed KMS, seeds are recoverable by the trusted backend process, and recovery-code delivery is a one-time browser response. Production still requires managed key storage/rotation, secure recovery procedures, and monitoring.

## Privileged MFA enforcement (Phase 22)

`MFA_REQUIRE_PRIVILEGED` defaults to `true`. With enforcement enabled, a correct password for an ADMIN or SECURITY_ANALYST without enrolled MFA creates a ten-minute `ENROLLMENT` challenge instead of an access token. The signed token has a distinct purpose claim, and its challenge row is stored with a purpose discriminator. It is rejected by `JwtAuthenticationFilter`; the filter also refuses already-issued access tokens for privileged accounts that have no MFA while enforcement is active.

The challenge is a narrowly scoped capability accepted only by `POST /api/auth/mfa/required-enrollment` and `POST /api/auth/mfa/required-enrollment/confirm`. The first operation creates an encrypted pending seed; the second verifies a fresh TOTP counter, enables MFA, consumes the challenge, creates hashed recovery codes, records the MFA/login audit events, and returns the first regular access token with recovery codes. Both responses are `Cache-Control: no-store`, and the enrollment operations share the login rate limiter. Ordinary protected routes remain unavailable before confirmation. Normal MFA-enrolled logins continue to use the five-minute login challenge.

Setting `MFA_REQUIRE_PRIVILEGED=false` preserves Phase 21's optional mode: a privileged account without MFA receives a normal access token, while an account that has chosen to enable MFA still must complete its second factor. Changing the environment value takes effect after the backend container is recreated. CI runs legacy and Phase 21 integration suites with enforcement disabled, then recreates the backend with enforcement enabled for Phases 22–26; a policy unit test covers both policy modes.

## MFA recovery-code rotation (Phase 23)

`POST /api/auth/mfa/recovery-codes/rotate` is limited to MFA-enabled ADMIN and SECURITY_ANALYST principals and requires both the account password and a fresh TOTP code. It does not accept a recovery code to authorize rotation. The user row is locked while the code counter is verified; in one transaction, the counter is advanced, every existing recovery-code hash is deleted, ten new random codes are hashed and stored, and `RECOVERY_CODES_ROTATED` is appended to `mfa_security_audits`. A failed password or replayed/invalid TOTP code leaves the current recovery-code set and audit history unchanged. The response contains the new raw codes once with `Cache-Control: no-store`; rotation does not revoke the active access token. Losing both the authenticator and all recovery codes requires the separate MFA-enabled ADMIN recovery workflow added in Phase 26.

## MFA management rate limiting (Phase 24)

The bounded peer-address limiter also runs before MFA enrollment start/confirmation, disable, recovery-code rotation, and the admin-assisted MFA recovery endpoint. Login, second-factor verification, and required-enrollment operations already use the same per-peer budget. Exceeding the configured `AUTH_LOGIN_RATE_LIMIT_MAX_ATTEMPTS` in the `AUTH_LOGIN_RATE_LIMIT_WINDOW_SECONDS` window returns `429 AUTH_RATE_LIMITED`, `Retry-After`, and a `Cache-Control: no-store` response before the password/TOTP proof is evaluated. Rate-limited calls do not reach the MFA service and therefore cannot consume a TOTP counter, replace recovery codes, or write an MFA audit event. The limiter is process-local; deployments with multiple backend replicas must use a shared rate-limit store or gateway.

## MFA recovery with an unused recovery code (Phase 25)

`POST /api/auth/mfa/disable/recovery-code` is restricted to enabled ADMIN and SECURITY_ANALYST accounts with MFA. It requires the account password and an unused recovery code (distinct from any code already consumed at sign-in). Under the user-row lock, the service verifies and marks that code used, disables MFA, deletes all remaining recovery-code hashes, increments `mfa_auth_version`, and appends `RECOVERY_CODE_USED` and `DISABLED` events in one transaction. Thus, audit-write failure rolls back the code use and factor change; success invalidates all existing access tokens and returns only a no-store disabled-status response. When privileged MFA enforcement is on, the next password login can only receive the narrow required-enrollment challenge. The browser explains that users need a second unused code after using one to sign in. When no unused code or authenticator remains, a different MFA-enabled ADMIN can recover an enabled ADMIN or SECURITY_ANALYST target through Phase 26.

## Admin-assisted MFA recovery (Phase 26)

`POST /api/admin/mfa/recovery` is restricted to an enabled, MFA-enabled ADMIN operating on a different enabled ADMIN or SECURITY_ANALYST whose MFA is enabled. The request carries the acting administrator’s own password and a six-digit TOTP code. The endpoint shares `LoginRateLimiter`, returns `Cache-Control: no-store` on success and proof/eligibility errors, and never discloses a target seed or creates recovery codes. The server validates the actor role and factor from the locked database row rather than trusting the JWT role alone.

The service resolves the target, then locks actor and target rows in ascending user-ID order to limit deadlocks. Password and unused fresh-TOTP proof are checked before mutation; the actor’s accepted counter is advanced. Within the same transaction the target’s MFA is disabled (clears active/pending seeds and increments `mfa_auth_version`), all target recovery-code hashes and login/enrollment challenges are deleted, and one `ADMIN_MFA_RECOVERY` audit event is appended. The audit retains the target’s existing `userId` / `username` fields and snapshots the actor’s `actorUserId` / `actorUsername`; newly written self-initiated MFA events also identify the user as actor. V17 keeps actor columns nullable so existing immutable history remains valid; the API returns null actor fields for those legacy rows. The append-only trigger and actor/user foreign keys remain in force.

Invalid target state, a self-target, wrong actor password, invalid/replayed TOTP, audit insert failure, or database failure leaves target changes uncommitted. After success, old target access tokens fail the MFA-auth-version check and old target challenges are unusable because their rows are gone. Mandatory policy requires the target to complete fresh enrollment on next password sign-in; optional mode permits password-only sign-in until the target enrolls again. The recovery decision still relies on the administrator verifying that the target has actually lost their factors; a compromised ADMIN credential plus MFA factor can perform recoveries and should be governed by out-of-band enterprise procedures.

## PostgreSQL roles and audit-trigger ownership

PostgreSQL uses three distinct roles. `POSTGRES_USER` / `POSTGRES_ADMIN_PASSWORD` is the administrative identity used by the one-shot Compose `db-roles-init` service. `DB_MIGRATION_USERNAME` / `DB_MIGRATION_PASSWORD` is the non-superuser Flyway identity, supplied to the trusted database/bootstrap containers and the separate `db-migrate` CLI container. `DB_USERNAME` / `DB_PASSWORD` is the application runtime identity used by the Spring datasource for request, audit, and telemetry DML; the backend container does not receive the migration username or password.

The migration role owns the `public` schema, Flyway-managed tables/sequences/views, and the append-only trigger function. It has schema `CREATE` so Flyway can create/alter objects. The runtime role has only schema `USAGE`, `SELECT`/`INSERT`/`UPDATE`/`DELETE` on application tables, and sequence `USAGE`/`SELECT`; it is not an owner, has no role memberships or elevated cluster flags, and cannot create schema objects, temporary objects, alter tables, or disable/drop triggers. It can append audit rows; V10's triggers reject changes to the four business audit histories, and V11/V13/V14 add append-only protection to authentication attempts, credential lifecycle, and MFA security history respectively. V17 expands the MFA audit operation constraint and adds actor snapshots without modifying legacy append-only rows. The PostgreSQL administrator, migration, and runtime passwords must all be distinct. Flyway migrations run in a separate one-shot `db-migrate` service before backend startup, so even a full backend-process compromise does not expose the migration credential through its environment. The migration and PostgreSQL administrator credentials remain trusted deployment/database principals.

Compose orders `db-roles-init` after PostgreSQL health, then `db-migrate`, then backend startup. The bootstrap and migration steps are one-shot services run when the stack is created/recreated. `db-roles-init` idempotently creates/reconciles both logins, removes runtime ownership on existing `public` application tables/sequences/views, clears excess runtime privileges on the database and `public` schema/tables/sequences, and transfers existing `public` table, sequence, view, schema, and audit-function ownership to the migration role. `db-migrate` runs the checked-in SQL migrations using the Flyway CLI, then exits before the backend starts. This upgrades a Phase 13 volume in place; do not delete the database volume to obtain the role separation. For an existing volume, keep `POSTGRES_ADMIN_PASSWORD` equal to the current stored administrator password so the bootstrap can connect. The database administrator and migration identity remain trusted DDL principals and can still disable the triggers; this is a privilege boundary against ordinary application-runtime SQL, not tamper-proof or immutable storage.

## Role-based management and access checks

The bootstrap administrator comes from local environment variables. Bootstrap never promotes an existing regular account. Public registration always assigns `USER` and cannot accept a role.

- `ADMIN`: manage devices/policies and device MQTT credentials/status; read devices, policies, authentication-attempt, access and MFA-security audits, ownership-transfer, status-change, and policy-change history, and telemetry.
- `SECURITY_ANALYST`: read devices, policies, authentication-attempt, access and MFA-security audits, ownership-transfer, status-change, and policy-change history, and telemetry.
- `USER` / `DEVICE`: eligible requester roles for API access-decision evaluation; protected telemetry reads additionally require an enabled `USER` owner. They cannot manage policies/devices or read management/audit/telemetry history endpoints.

`POST /api/access/check` and the protected telemetry route derive requester ID/name/role from the bearer-token principal. The caller cannot claim another account or submit trusted device type/status. Management roles receive a recorded business `DENY` (`REQUESTER_ROLE_NOT_ALLOWED`) rather than overriding resource policy. The decision endpoint returns HTTP 200 for an evaluated DENY; the protected telemetry route returns HTTP 403 and no resource data on DENY. For this route, an enabled `USER` must also own the target device; only an ADMIN can transfer ownership, and only to an enabled `USER`. The generic decision endpoint remains a policy demonstration and does not fetch protected data or enforce ownership. Missing/invalid authentication remains HTTP 401.

## Decision order and policy

`ZeroTrustDecisionService` loads the registered device by normalized device code while holding a pessimistic row lock. Device type is the policy subject; the client supplies only the device code, resource, and action.

1. Verify the requester role is eligible for the channel (`USER`/`DEVICE` for API; `DEVICE` internally for MQTT).
2. Require a registered device.
3. Require status `ACTIVE`; `INACTIVE`, `BLOCKED`, and `REVOKED` are denied.
4. Query enabled exact subject/resource/action policies. An explicit `DENY` is selected before `ALLOW`.
5. If no policy matches, return default `DENY`.
6. For an otherwise-allowed protected-resource API read, require the JWT requester to match the device owner; otherwise return `DENY` (`DEVICE_NOT_OWNED`). This check does not apply to MQTT ingestion or the decision-only `/api/access/check` endpoint.
7. For an otherwise-allowed MQTT request, require a sequence greater than the device's last accepted sequence; stale/repeated messages are denied as `REPLAYED_MESSAGE`.
8. Persist the outcome/reason and context in `access_audits`.

An MQTT high-water mark is advanced only for an allowed message and in the same database transaction as telemetry persistence. Device row locking serializes concurrent messages; the telemetry table also enforces uniqueness on `(device_id, device_sequence)`. A message denied by device status or policy is not persisted. Explicit policy DENY and default DENY retain precedence over replay acceptance.

No role, device status, or policy miss can be overridden by a matching ALLOW rule. `ProtectedResourceService` queries recent telemetry only after the decision service returns ALLOW; on DENY, it returns an empty telemetry array without running a telemetry query. The policy table does not support wildcards or contextual expressions.

## Management-change audit history

Successful actual device-status transitions are stored in `device_status_audits` with previous/new status, device ID/code, the authenticated ADMIN ID/username, and timestamp. `PATCH /api/devices/{id}/status` and `DELETE /api/devices/{id}` update status and insert the event in one transaction. Repeating the current status or revoking an already-revoked device is a no-op and creates no event. The status audit is separate from the per-message `DEVICE_NOT_ACTIVE` access-decision audit.

Policy CREATE/UPDATE/DELETE operations are recorded in `policy_change_audits` with before/after snapshots and the authenticated ADMIN actor/timestamp. CREATE has only after state; UPDATE has both; DELETE has only before state. The mutation and event insert share a transaction; failed requests and semantically unchanged updates do not produce successful-mutation events. Policy history is keyed by a scalar policy ID rather than a policy foreign key, preserving DELETE history. `GET /api/devices/{id}/status-audits` and `GET /api/policies/{id}/audits` are restricted to ADMIN and SECURITY_ANALYST and use bounded 1–100 record pages. These typed management histories do not replace `access_audits` or `device_ownership_audits`. Phase 12's `page`, `size`, inclusive `from`/`to`, and event-specific filters affect read selection only: they do not grant new roles, alter stored events, or change policy evaluation. Page sizes are capped at 100 and malformed/reversed query ranges are rejected with HTTP `400`. Flyway V10 installs PostgreSQL triggers on the four business audit-history tables, and V11 adds the same row UPDATE/DELETE rejection to authentication-attempt history. Phase 14 gives the backend's runtime datasource no table/schema ownership or DDL privileges, so ordinary runtime SQL cannot disable/drop those triggers. The migration role and PostgreSQL administrator remain trusted DDL principals; this is not tamper-proof storage against them.

## MQTT credentials and ACLs

Mosquitto Dynamic Security is the broker authentication/authorization point. Each device has its own random 256-bit password, username equal to its normalized device code, and registered MQTT client ID. The create/rotate API also generates an Ed25519 signing key pair; PostgreSQL stores only the public key, while the private key and MQTT password are returned once with `Cache-Control: no-store`. The broker, not PostgreSQL, stores the MQTT credential verifier. Rotation replaces both the broker password and signing key. Device accounts remain enabled across status changes: the per-device topic ACL still bounds publish scope, then the backend validates the application signature and device status before policy/replay checks. It records `DEVICE_NOT_ACTIVE` for non-active signed messages before discarding them. The backend uses a different subscriber account and a separate role.

- Each device gets a unique role `zt-device-{deviceCode}` with one literal `publishClientSend iot/telemetry/{deviceCode} allow` ACL. The broker therefore rejects cross-device topic publishes.
- Backend role: subscribe/receive only on `iot/telemetry/+`.
- Anonymous connection: disabled.
- Unmatched publish/subscribe/receive/unsubscribe: denied by default (with explicit backend receive/subscription ACLs).
- Retained publishes: disabled for this prototype.

Wrong credentials, a mismatched client ID, or a publish to another device's topic are rejected at the broker before the backend sees the message; those attempts appear in Mosquitto logs, not in `access_audits`. Broker access does not override the backend's active-device check, policy evaluation, explicit DENY, default DENY, or replay check.

The MQTT payload is a JSON envelope with unpadded-base64url `payload` and `signature` fields. The decoded `payload` is the exact UTF-8 telemetry JSON byte sequence signed with the provisioned Ed25519 private key; verification uses the public key stored for the device named by the authorized topic. Verification occurs before business fields are parsed or submitted to policy/replay evaluation, preventing unauthorized content changes from advancing the sequence. Invalid signatures are recorded as `DENY` / `INVALID_DEVICE_CREDENTIAL` without storing the untrusted sequence. Malformed envelopes/payloads rejected before evaluation are logged by the subscriber and are not access-audit events. Existing device rows without a public key must rotate credentials to receive a signing key before signed telemetry can be ingested.

The generated CA/certificates are for a local demo, not a PKI deployment. Keep `.env`, device signing keys, and `mosquitto/tls/ca.key` private; local TLS files are ignored by Git. Do not expose the broker or admin credentials to untrusted networks. There is no device-certificate TLS authentication, credential expiry, automated CA rotation, or production secret-management system.

## Device credential audit history (Phase 20)

Device provisioning and signing-key rotation events are written to `device_credential_audits` within the same database transaction as the device record/public-key update. The event snapshots the authenticated ADMIN actor and device code, and stores only SHA-256 fingerprints of the old/new Ed25519 public keys. MQTT passwords, signing private keys, and raw public-key encodings are excluded. PostgreSQL rejects UPDATE/DELETE through the append-only trigger; the backend runtime role has no ownership or DDL privileges. ADMIN and SECURITY_ANALYST may query filtered, bounded pages, while USER callers receive `403`. Provisioning/rotation response secrets remain one-time and use `Cache-Control: no-store`.

## Web console (Phase 19)

The React/TypeScript SPA is a client for the existing API, not an enforcement boundary. Compose serves the static assets with Nginx on a loopback-bound port and proxies relative `/api` calls to the backend; browser CORS is not enabled. The UI hides management actions according to the authenticated role, but Spring Security and service-layer authorization remain authoritative. The bearer token is held only in application memory and is cleared on sign-out, session expiry, or tab reload—not written to Web Storage. One-time MQTT passwords and signing private keys remain in the provisioning dialog's component state until it is closed; they are not added to local storage or logs.

The UI and API proxy are intended for the local demo. In Compose, the backend sees the frontend container as the login connection peer; the Phase 17 limiter does not trust forwarded-IP headers, so requests through this single proxy share the same process-local peer bucket. This is not a production reverse-proxy/IP attribution design.

## Audit and limitations

Every evaluated API decision and MQTT policy/status/replay decision is recorded in `access_audits`, including DENY outcomes. Invalid signed MQTT messages are also recorded as `INVALID_DEVICE_CREDENTIAL` without an untrusted sequence number. Protected-resource ownership failures are recorded as `DEVICE_NOT_OWNED` (including any matched ALLOW policy snapshot) before telemetry is queried. MQTT audit rows include the device sequence only after signature verification. Successful owner transfers, actual device-status transitions, policy CREATE/UPDATE/DELETE mutations, device credential provisioning/rotation, and MFA enrollment/disable/recovery-code-use events are separately recorded in typed management-audit tables, with actor identity and timestamp. The credential lifecycle history stores only SHA-256 fingerprints of public signing keys; MQTT passwords and private signing keys are never persisted. MFA security history records target/account snapshots, actor snapshots for new events, and operation type only; it does not record authenticator seeds, TOTP values, challenges, passwords, or raw recovery codes. Validated API login attempts are recorded separately in `authentication_attempt_audits`; they are not business access-decision events. Initial device ownership, status no-ops, semantically unchanged policy updates, and failed management mutations do not produce change events. Policy-history reads remain available by policy ID after the policy is deleted. `GET /api/auth/audits`, `GET /api/auth/mfa/audits`, `GET /api/access/audits`, `GET /api/devices/{id}/ownership-audits`, `GET /api/devices/{id}/status-audits`, `GET /api/devices/{id}/credential-audits`, `GET /api/policies/{id}/audits`, and `GET /api/telemetry` are available only to `ADMIN` and `SECURITY_ANALYST`; audit-history pages contain at most 100 records. Broker authentication and ACL rejections and malformed MQTT messages rejected before decision evaluation are not database access-audit events.

The access-check endpoint remains a decision demonstration; `GET /api/resources/devices/{deviceCode}/telemetry` enforces ownership and policy for this demo resource only, not arbitrary network traffic. Device ownership is managed by ADMINs and applied to this protected HTTP route; it is not an MQTT ownership rule. MQTT uses authenticated per-device broker credentials, per-device topic ACLs, verified TLS, Ed25519 application signatures, and monotonic sequence replay detection. Key delivery is a prototype one-time API response; hardware-backed key storage, certificate lifecycle automation, credential expiry, MFA enforcement for non-privileged accounts, distributed production rate limiting, production secrets management, and enforcement on arbitrary resources are not implemented.
